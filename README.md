# 教室故障与临时改排工作台（浏览器端）

面向校园后勤的**纯浏览器端**教室故障报修、事故封闭、工单维修、课程临时改排与**无障碍出行保障**工作台。
技术栈：**React 18 + TypeScript + Vite + IndexedDB + WebWorker + Vitest**，无后端、无外部依赖，
所有数据保存在浏览器本地 IndexedDB，所有状态变更以**只追加事件流**记录，可随时回放。

## 1. 架构与职责

```
src/
├─ types.ts                 领域模型与事件定义（事件溯源，含无障碍出行）
├─ db/idb.ts                手写 IndexedDB Promise 封装（events/blobs/drafts/kv）
├─ engine/
│  ├─ reducer.ts            纯函数事件回放：事件流 -> 当前快照
│  ├─ scheduling.ts         排课引擎：候选过滤、方案一/方案二、重叠硬校验
│  ├─ commands.ts           命令层：操作 -> 事件（合并、门控、通知版本、草稿冲突）
│  ├─ routing.ts            出行路由：时间展开图 + 地点图两种计算表示（含统计量）
│  ├─ transit.ts            出行业务引擎：候选规划、护送员调度可行性、派生状态
│  ├─ transitCommands.ts    出行命令层：原子确认、执行状态机、途中交接、扰动
│  ├─ scenario.test.ts      改排业务规则测试（15 个）
│  ├─ transit.test.ts       出行与路由测试（18 个）
│  └─ idb.test.ts           IndexedDB 持久化/回放测试（2 个）
├─ worker/
│  ├─ incident.worker.ts    WebWorker：事件唯一写入口、回放快照、排课/候选计算
│  └─ client.ts             Worker Promise 客户端
├─ state/store.tsx          React Context：快照、角色、在线开关、模拟时钟、草稿
├─ views/                   教师/设施/调度/维修/无障碍出行/资源/事件回放 七个工作台
└─ lib/seed.ts              种子数据：教室课程、O/S/W/C 路网、班次、学生分组、护送员
```

关键设计：

- **事件溯源 + 可回放**：业务状态（事故、封闭、工单、方案、通知、出行行程）全部由事件回放得到，
  IndexedDB `events` 表只追加；“事件回放”页提供 seq 滑块，可查看任意历史时刻快照。
- **WebWorker 承担计算与持久化**：回放、DFS 换房搜索、候选教室评估、出行候选计算都在 worker 线程，
  主线程只发消息、渲染 UI。
- **照片存 IndexedDB Blob**：不上传任何服务器，通过 ObjectURL 预览。

## 2. 本地启动

### 方式 A：Docker Compose（一键启动，推荐）

```bash
docker compose up -d --build
# 打开 http://localhost:8080
docker compose logs -f          # 查看日志
docker compose down             # 停止
```

多阶段构建：Node 22 编译静态资源 → Nginx 1.27 托管（含 SPA 路由回退与静态资源缓存）。

### 方式 B：本地开发（Node 22）

```bash
npm ci                 # 或 npm install
npm run dev            # 开发服务器，默认 http://localhost:5173
npm run build          # 类型检查 + 生产构建到 dist/
npm run preview        # 本地预览生产构建
```

### 测试

```bash
npm test               # vitest run，共 35 个用例
```

> 本隔离容器内未安装 Docker 守护进程，Dockerfile/compose 已按标准多阶段构建编写，
> 实际镜像构建与容器启动需在装有 Docker 的环境执行；容器内已实际执行的是
> `npm test`、`npm run build` 与 `vite preview` HTTP 冒烟验证（见第 7 节）。

## 4. 无障碍出行（连廊封闭后的两组学生护送/接驳）

### 4.1 场景与资源

- 连廊（O↔C 直达，5 分钟）封闭中；四名需要无障碍协助的学生分两组：
  **第一组** 08:50 从 O 出发、09:10 前到 C 楼；**第二组** 09:10 出发、09:30 前到。
  每组两人，各含 1 名轮椅学生。学生可选**步行护送**或**登记接驳**，两种服务都可办理。
- 步行路网（均为已批准无障碍路径）：O↔S 2 分钟、O↔W 10 分钟、W↔C 10 分钟。
- 班车 S→C：8 分钟，**4 座 + 1 个轮椅固定位**，09:00 与 09:20 两班。
- 护送员 2 名（李/王），08:45-10:00 可用，每人最多同时带 2 人。
- 样例答案：步行 09:10/09:30 到；接驳 09:08/09:28 到（O→S 2 分钟 + 候车 + 8 分钟车程）。

### 4.2 两种计算表示（同一套算法组织，无算法选择按钮）

每次“计算候选”都同时运行两种实现并互相校验到达时刻一致：

- **时间展开图**：地点 × 窗口内每分钟 = **4 × 76 = 304 个地点时刻点**，
  等候边 4 × 75 = **300** 条，步行边实例 412 条、班次边实例 2 条（计数随封闭/取消变化），
  等候与班次显式成边，Dijkstra 求最早到达；窗口增大时状态随之增多。
- **地点图**：只保留 **4 个地理节点**与到达标签，遍历到班车边时**查询下一班可乘车次**
  （不假设随时有车），边上的等车时间现算；UI 与测试都记录实际的**班次查询量**、
  步行松弛次数等统计量，而不是只写复杂度名称。

所有输入为整分钟、步行耗时非负、允许在合法地点等待；查询固定在同一份路网/班次/资源快照上。

### 4.3 确认与执行规则

- **候选计算不占座**；点“确认登记”时才以最新快照重算候选并**原子核对**：
  同行者（两人同车次同阶段）、车次座位/轮椅固定位、护送员时间与位置（重复派单不能让
  同一人在两处带队，调位按步行路网可达性校验）。任一不足即**退回重算**，原安排不受影响。
- 上下车、交接给教师、确认到课**分别记录**；车程结束或通知已发 ≠ 学生已到，
  全组都确认到课后行程才完成。
- 每个护送阶段另存**实际负责的学生集合**（确认接到时写入）；护送员未接到本人不得登记上车。
- 护送员实际位置由**模拟行程**推出（资源面板可见）；途中交接只能在全组位于地点节点时进行，
  **原责任保持到接续者实际确认**才解除。
- 扰动（取消 09:00 班次、关闭 W→C、护送员请假、09:20 临时满载）**不自动改行程**：
  受影响行程标红，两种方式都需按**新的合法候选重新确认**；原安排保留为“已被替代”，
  未接收通知者保留待办（旧通知可能晚到，版本 v1/v2 递增、旧版自动作废）。
- **设施解除封路前**，任何重算都不会自动恢复直达连廊；解除后新候选才包含 O↔C 直达边，
  且既有行程保持原样。

## 6. 本题场景验证步骤（手工操作脚本）

> 任何时候可在“事件回放”页点“重置演示数据”回到初始状态。

### A. 改排流程（步骤 1-6 同前）

1. **林老师** 09:40 扫 `B-B201` 报“漏水”；**周老师** 09:45 扫 `B-B202` 报“漏水” →
   设施工作台可见两条报修合并为同一事故（第二条标“重复报修·已合并”）。
2. 设施核准边界（预计 12:00 修复）→ B201/B202 封闭；生成工单 → 维修工作台可见。
3. 调度工作台候选核查逐间列出不合格原因；方案一 = 516 学生分钟，方案二 = 402（少 114）。
4. 采用方案 → 各班教师确认 → 发布，师生收到同版本 v1 通知。
5. 维修标记已修复（封闭不变）→ 11:30 复测失败（维持封闭，安排不回滚）→
   14:00 复测通过才解封（已发布安排仍保留）。
6. 离线草稿：课程结束后提交判**过期**；课程被改排后提交判**冲突**。

### B. 无障碍出行流程

1. 时钟设 **08:45**，身份切到**陈调度**，打开“无障碍出行”。
   第一组选“步行护送”点“计算候选”：可见两种实现的统计（展开图 304 状态点/300 等候边；
   地点图 4 节点/班次查询量），最早 09:10 到；再切“登记接驳”计算：09:08 到（含候车段）。
2. 点“确认登记”：第一组步行由李护送负责（08:50-09:10）。第二组同样办理步行
   （候选评估显示李护送 09:10 在 C 无法赶回 O，只能派王护送）→ 确认。
   若改选接驳，两名护送员可共用：李护送送完第一组到 S（09:00）后回 O 接第二组。
3. 执行跟踪：时钟 08:46，李护送“接单”；08:50“确认接到学生”（写入实际负责集合）；
   资源面板可见 09:05 李护送位于 W→C 步行段（模拟行程）。09:10 到达后“交接给接收教师”，
   切到**林老师**“确认到课”——全组到课后行程才完成。
4. **扰动演示**（时钟 08:45-08:48 操作效果最佳）：
   - 点“取消 09:00 班次”：已确认的接驳行程标红“班次已取消”，原安排保留；
     第一组接驳重新确认不可行（09:20 到 09:28 超截止），按新候选改确认**步行**（09:10 到），
     通知升 v2、v1 作废，护送员/接收教师待办保留直到接收。
   - 点“09:20 临时满载”：第二组接驳候选因“轮椅固定位不足”被退回重算。
   - 点“王护送请假”：第二组步行重订无护送员可用，只能改接驳。
   - 点“关闭 W→C 道路”：步行候选不可行，只能接驳。
   - 多轮扰动后直达连廊仍封闭；切**王设施**点“设施解除连廊封闭”后，
     新候选出现 O→C 直达（08:55 到），既有行程保持原样。
5. **途中交接**：第一组步行接到学生后，时钟 09:00（全组在 W），
   在执行跟踪里选择王护送“途中交接”——原责任到接续者实际确认才解除；
   09:05（路段途中）尝试交接会被拒绝。
6. **旧通知晚到**：重新确认产生 v2 后，护送员先“接收”v1（已作废）待办仍在并提示
   “持有的 v1 已作废”，接收 v2 后待办清除。

## 8. 数据与隐私

全部数据（事件、草稿、照片、出行行程）仅存在当前浏览器的 IndexedDB（库名
`incident-workbench-db`），不发起任何网络请求；清空浏览器站点数据或使用页内
“重置演示数据”即可恢复初始状态。
